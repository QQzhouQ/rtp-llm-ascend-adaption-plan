### 1.2 Ascend 关闭多模态的两个门（均为加载期）

```python
# models/qwen3_next/qwen3_next.py::_parse_mm_config   (qwen35 家族)
if is_ascend(): return                    # is_multimodal 保持默认 False (ModelConfig.h:37)

# models_py/model_desc/qwen3_next.py::word_embedding
if _IS_ASCEND: return self.embed_tokens(input_ids)   # 跳过 mm 注入
```

注：`qwen3_vl.py::_from_config_json` 里 `is_multimodal = True` 是**无条件**的——
即 qwen3_vl 注册的模型在 Ascend 上加载会直接走 mm 构建路径（这正是历史上
"ViT 按 CUDA 设备串构建并断言" 的来源）。

## 二、vLLM-Ascend 实现考证（/home/d30033799/vllm-ascend）

### 2.1 核心证据：`vllm_ascend/patch/worker/patch_qwen3vl.py`

对 Qwen3-VL 的全部 NPU 适配只有三件事：

1. **ViT（`Qwen3_VisionTransformer`）零改动**：不做任何注意力/算子替换，
   HF/vLLM 的纯 torch ViT（SDPA/eager 注意力）在 torch_npu 上直接运行
2. `fast_pos_embed_interpolate`：纯 torch 的位置编码插值优化（可选性能补丁）
3. `deepstack_input_embeds` 的 TP 分块包装（纯 torch chunk）

LLM 侧补丁与本调研无关（mrope 的 triton-ascend kernel、qkv+rmsnorm 融合）。

### 2.2 结论性事实

- vLLM-Ascend 官方支持 Qwen2.5-VL / Qwen3-VL / Qwen3-VL-MoE 系列端到端
- 视觉塔不需要专用 NPU 注意力后端（torch_npu 的 SDPA/dispatch 足够）
- 图像预处理全在 CPU（HF processor），与设备无关
- MRoPE 的 NPU 数值正确性我们已独立验证（两个 PR 的对拍测试）

## 三、可行性结论

| 环节 | 难度 | 依据 |
|---|---|---|
| ③ mm 注入开门 | 极低 | 代码已存在（纯 torch），删门+验证即可 |
| ② ViT 前向 | 低-中 | vLLM-Ascend 证明零改动可跑；需验证 HF 版本在我们环境的行为（SDPA 路径、dtype） |
| ① C++ mm processor | 中 | MMProcessorConfig 逻辑设备无关；需排查 ingress 装配中的 CUDA 假设（下载头、trt 开关等）与 VitConfig 默认值 |
| MRoPE | 已完成 | 两 PR 交付 |

**主要风险**：
1. HF transformers 版本差异（rtp-llm 锁 5.2.0，Qwen3VLVisionModel 接口随版本变化）
2. ViT 的 SDPA 在 torch_npu 的数值/性能（vLLM-Ascend 已验证同款，风险低）
3. C++ ingress 的隐含 CUDA 假设数量未知（只能逐个排）
4. 大图 batch 下的 NPU 内存（视觉特征较长，KV 与激活叠加）
