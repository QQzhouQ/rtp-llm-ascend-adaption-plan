4.2 NormalEngine 与 FIFOScheduler：调度循环

NormalEngine 只管“每步问调度器要一个 batch”，真正的取舍逻辑在 engine_base/schedulers/FIFOScheduler。这一节把两者拆开看：先看线程与调用点，再看 FIFOScheduler 的队列、状态机、准入判据和 group 车道。

4.2.2 四条队列 + 状态机

每个请求在调度器里是一个 GenerateStream，状态只有四个（engine_base/stream/GenerateTypes.h:178-183）。addStreamToNewState（FIFOSchedulerBase.cc:231-249）负责把状态映射到具体队列：

状态进入的队列含义
WAITINGwaiting_streams_已入队，等准入。可能因 batch 满、token 预算不足或 KV 容量不足而留在队首。
LOADING_CACHEloading_cache_streams_KV block 已分配，等 connector 把前缀缓存 H2D 拷进来（PD 分离 / prefix cache 场景）。
RUNNINGrunning_streams_当前参与执行的 batch 成员；本轮 schedule 的返回值就是这个列表的全量。
FINISHED不进入任何队列结束或报错，直接从列表移除；结果由 GenerateStream 的输出队列交回 RPC 层。

此外还有一条临时队列 new_streams_：本轮新准入的 stream 先放这里，schedule() 末尾才 splice 进 running_streams_（FIFOScheduler.cc:685-686），这样“本轮新增”和“历史在跑”可以分开计数。

状态推进的触发 推进统一走 stream->moveToNext()：准入时上报 StreamEvents::CanRun，KV 分配完成时记录 LoadInitiated。调度器不直接改状态，只负责“上报事件 → 让 stream 自己算下一状态 → 搬到对应队列”这个循环。

4.2.3 一轮 schedule() 做什么

schedule()（FIFOScheduler.cc:575-691）全程持锁，四步：

1
等待可执行工作按队列状态选三档超时：10ms / 100ms / 无限。L576-586
2
推进状态清 schedule_trigger_，把结束/出错的流移出 running；batch 空了就把车道重置为 NONE。L588-597
3
选车道并准入group 加载完成优先；否则推进普通 cache load 与 waiting_streams_。L602-684
4
合并返回new_streams_ 并入 running_streams_，上报指标，返回整个 running 列表。L685-690
FIFOScheduler.ccL577-586（压缩）
if   (有 cache 加载 / group 待处理)   wait_for(10ms);   // 等 I/O 完成
elif (有 waiting 但没在跑)           wait_for(100ms);  // 等 PD 释放 block
else                                wait();            // 空闲，等 enqueue 唤醒

唤醒条件只有 stop_ / schedule_trigger_ / running_streams_ 非空；被容量阻塞的 waiting 不算唤醒事件，避免 KV 不足时自旋。

4.2.4 准入判据

WAITING 变 RUNNING 要过 evaluateRunningBatch（L130-160）四道闸门：

闸门判据不通过
① prefill / decode 互斥running 非空 → false等当前 batch 排空
② batch 数量running + admitted + 1 > max_generate_batch_size_留队等下一轮；DECODE 角色可补位
③ token 预算fitsPrefillTokenLimits(...)本轮不再准入，但继续扫后面的流
④ inited-KV 流数max_inited_kv_cache_streams_ > 0 时统计 curBlocksNum() > 0留队；0 表示不限
FIFOScheduler.ccL130-160 / L202-239（伪代码）
if (role == DECODE) return running + admitted + 1 <= max_gen_batch;   // 可补位
if (!running.empty()) return false;                            // ① 互斥
if (running + admitted + 1 > max_gen_batch) return false;      // ② 数量
available = max_batch_tokens - running.size();                // ③ 预算
if (admitted >= available || cand >= available - admitted) return false;
return seq_count <= (available - 1) / max_seq_len;             // padded 矩形面积

预算有两种口径：WithCache 含复用的 prefix，WithoutCache 只算重算 token（max_batch_tokens_without_cache 卡后者）。

4.2.5 group 车道：enqueueGroup 的隔离执行

批量接口可以一次提交一组必须同批执行的请求（例如同一 batch 的评测样本）。enqueueGroup（L82-128）把整组放进 waiting_group_queue_，并保证该组独占一个执行边界，不与普通请求混批。

准入

整组必须一起过闸：evaluateWaitingGroupQueue（L495）逐成员调 evaluateRunningBatch，失败成员留在组内，已成功的进入 admitted_streams。每轮最多尝试一个 group。

降级

若 group 大小超过 max_generate_batch_size_ 或 max_inited_kv_cache_streams_，直接回退成普通单流入队（L101-123），并累加 group_fallback_count 指标。

三个车道状态由 AdmissionLane 表示：NONE（batch 已排空，可重新选）、NORMAL（普通请求占着边界）、GROUP（group 占着边界）。prefer_group_next_ 是公平性开关：普通车道发现 group 在排队时，本轮不再准入新普通请求，让当前 batch 尽快排空给 group 让路；反过来，如果普通请求全被 KV 阻塞，也会退让去试一个 group，避免两条车道互相 head-of-line 死锁（L649-682 的长注释即为此）。

08

KV Cache 与混合状态

35B 的“缓存”不止 KV：full attention 用分页 K/V，GDN 用卷积状态与 SSM 状态。三者共享同一个 block 管理器，但按 group 维护不同物理布局。

三类状态

Full attention K/V
分页 [blocks, 2, page, kv_heads×head_dim]（BSND 视图），FIA v2 读取，scatter 写入。
GDN conv state
每层卷积历史（宽度 3），随 causal_conv1d 更新。
GDN SSM state
每层 [value_heads, DV, DK] 的 V-first 分页状态；kernel 内部转为 K-first [HV, DK, DV] 视图（linear_attention.py:276-280）。

Group 与 block table

kv_cache_spec_descs 由 build_hybrid_kv_cache_spec_descs(..., KVCacheSpecType.MHA) 生成（models/qwen3_next/qwen3_next.py:181-185）。C++ 组 batch 时把 block table 传成 3-D [group, batch, blocks]（PyWrappedModel.cc:440-493），Python 再按 tag 取对应 group（model_desc/block_map.py）。

8.1 slot_mapping 与 KV 写入

compute_ascend_attn_params（ascend_attn_params.py:59-90）在 CPU 上纯 Python 计算每个 token 的 positions 与 slot_mapping，然后搬到 NPU。它替代了 C++ 的 FlashInferMlaAttnParams.fill_params()，且必须使用 kernel 粒度 block table，才能与 kv_cache_base 的视图和 FIA 的 block table 对齐。

rtp_llm/models_py/modules/factory/attention/ascend_impl/ascend_kv_cache_write_op.pyL26-41
kv_base = kv_cache.kv_cache_base          # BSND [blocks, seq, heads, dim]
k_view  = kv_base[:, 0]
v_view  = kv_base[:, 1]
slot_mapping = self.params.slot_mapping
torch_npu.npu_scatter_pa_kv_cache(key, value, k_view, v_view, slot_mapping, cache_mode="Norm")

8.2 GDN 状态的读写

Prefill 从分页池读初始 state（load_initial_state_from_block_map），chunk 结束后把 final_state 写回（store_ssm_state_to_block_map，qwen3_next.py:695-704）；Decode 用 block_map + sequence_lengths_plus_1 定位并 inplace 更新（recurrent.py:179-215）。注意 Ascend 的 conv state 视图是 (pages, state_len, dim)，与 Triton 路径的 (page, dim, state) 不同，代码里用 _IS_ASCEND 分支区分（qwen3_next.py:788-807）。

容量与块大小 35B 部署设置 kv_cache_mem_mb=8192、seq_size_per_block=512、kernel_seq_size_per_block=512。FIA v2 推荐 page_size=128，但本分支因混合缓存断言只能 512/512；修改前先确认 OpDefs.h 的约束。

加载器先按 TP 切分，再做 NPU 需要的布局变换（顺序不能颠倒，因为 pair-split swizzle 会跨越 K 分组维）。

swizzle_scale_to_npu_layout（kernels/ascend/w8a8_mx_layout.py:32-60）把 [N, kp] 变为 [kp//2, N, 2]：先把 kp 补到偶数，再 reshape 成 [N, kp//2, 2] 并转置前两维。奇数 kp 的补位不属于任何权重组，值不参与计算。

9.3 量化识别与拒绝逻辑

AscendW8A8MXFP8Config（config/quant_config.py:530-567）只处理显式带 MXFP8 标记的层；裸 W8A8 可能是 INT8，不能被当作 MXFP8 加载。未被标记的模块进入 exclude_modules，保持高精度。get_supported_kv_cache_dtypes 仅 fp16/bf16，KV Cache FP8 不在本阶段范围。
