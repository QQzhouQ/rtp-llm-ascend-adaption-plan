### 2. `rtp_llm/cpp/cache/BlockPool.cc` —— NPU 显存池注册时别再被当成内存条

**评审说什么**：KV cache 池有一种"注册给缓存存储（MR 注册）"的机制。判断"这是不是显存"的代码只写了 `where() == MEMORY_GPU`，而 Ascend 的池返回的是新加的 `MEMORY_NPU`。结果 NPU 上的显存地址被当成**主机内存**去注册——类型标错了，后续 RDMA/缓存传输行为全都不对。

**改了什么**：两处（注册 `regUserMr` 和注销 `deregUserMr`）的判断从：

```cpp
const bool gpu = where() == MemoryType::MEMORY_GPU;
```
改成：
```cpp
// NPU pool addresses are device memory just like GPU; register with the
// device flag so the cache-store MR does not treat them as host memory.
const bool gpu = where() == MemoryType::MEMORY_GPU || where() == MemoryType::MEMORY_NPU;
```

**效果**：NPU 显存池按"设备内存"注册，和 GPU 行为对齐。

### 3. `rtp_llm/cpp/cuda_graph/cuda_graph_device_shims.h` —— 两件事：绑设备 + 真事件

这个文件是平台适配的"枢纽头文件"（CUDA/ROCm/Ascend 三平台分支都在这），修了评审提的两个 P1。

#### 3.1 异步工作线程没绑定 NPU（P1）

**评审说什么**：`AsyncRunner`（异步任务的工作线程）启动时会调用 `setDevice(stream.device_index())` 把线程绑到指定设备上。但 Ascend 分支的 `setDevice` 是**空操作**（`(void)rank;`）。多卡训练/推理时，非 0 号卡的线程可能跑在错误的 NPU 上分配显存。

**改了什么**：

```cpp
inline void setDevice(int rank) {
#if USING_ASCEND
    // 防 -1 这类非法索引静默绑错卡，直接报错
    RTP_LLM_CHECK_WITH_INFO(rank >= 0, "setDevice(rank=%d) requires a concrete NPU index", rank);
    aclError err = aclrtSetDevice(rank);          // 真正调用 CANN 的绑卡 API
    RTP_LLM_CHECK_WITH_INFO(err == ACL_SUCCESS, "aclrtSetDevice(%d) failed: %d", rank, ...);
#elif USING_ROCM
    ...（原有代码不变）
```

**配套**（见第 6 项 MtpExecutor）：原来 MtpExecutor 在 Ascend 上创建流用的是"不带卡号"的设备对象（index = -1），传给 `setDevice(-1)` 会失败。所以那边同步改成了带 `local_rank` 的具体卡号。

#### 3.2 事件 record/block 是空操作，静默破坏数据同步（P1）

**评审说什么**：`graphRecordEvent` / `graphBlockEvent` 在 Ascend 分支里就是 `(void)event; (void)stream;`——**什么都不干**。但下游有代码在非阻塞拷贝 D2H 之后 record 事件，消费方 `synchronize()` 等这个事件再读数据。事件从没被记录过，"等待"形同虚设，读到的可能是**没拷完的数据**。注释还写着"降级为流同步语义"，纯属说谎（实际啥同步都没有）。

**改了什么**：按评审给的第一方案，在**当前 NPU 流**上做真实 record/block：

```cpp
inline void graphRecordEvent(torch::Event& event, GraphStream stream) {
#if USING_ASCEND
    (void)stream;  // Ascend 的 GraphStream 是不透明句柄，改用当前 NPU 流
    event.record(c10_npu::getCurrentNPUStream().unwrap());
#else
    event.record(stream);
#endif
}
// graphBlockEvent 同理：event.block(c10_npu::getCurrentNPUStream().unwrap());
```

**为什么这样是对的**：
- `torch::Event(kPrivateUse1)` 在 torch_npu 里有真实实现（仓库里 `ExecOps.cc:166` 的 `runtimeCreateEvent` 早就用同样的写法，是经过验证的路径）；
- Ascend 是单流执行模型，所有异步 worker 都跑在默认流上，"记在当前流"恰好排在 D2H 拷贝之后，`synchronize()` 从此真正等待拷贝完成；
- CUDA/ROCm 分支一行未动。

**为编译补的头文件**（关键，否则任何引用这个头文件的代码都编不过）：

```cpp
#if USING_ASCEND
#include <acl/acl.h>                    // aclrtSetDevice / aclError
#pragma GCC diagnostic push
#pragma GCC diagnostic ignored "-Wunused-function"
#include <torch_npu/csrc/core/npu/NPUStream.h>   // c10_npu::getCurrentNPUStream
#pragma GCC diagnostic pop
```

已用本机 CANN 工具链 + torch_npu 头文件做过 `-fsyntax-only` 单独验证。

### 4. `rtp_llm/cpp/models/ModelTypes.cc` —— TP 并行时"谁在哪个设备"的表格要和打包逻辑一致

**评审说什么**（说人话版）：TP 并行要在多卡间广播输入。发送方（rank 0）先填一张"位图"告诉其他卡"这些张量在 GPU 上、那些在 CPU 上"，其他卡按位图分配同样类型的缓冲区，然后发送方把张量打包（设备的打进 GPU 缓冲、CPU 的打进 CPU 缓冲）广播出去。

**Bug**：填位图的代码只认 `is_cuda()`，而打包代码认 `is_cuda() || is_privateuseone()`（把 NPU 也算设备）。Ascend 多卡时：rank 0 把 NPU 张量打进 GPU 缓冲区，其他卡按位图以为那是 CPU 张量、分配了 CPU 缓冲——**两边对不上，广播出来的是垃圾**。

**改了什么**：位图生成统一用同一个谓词，六个字段（combo_tokens、input_lengths、sequence_lengths、prefix_lengths、lm_output_indexes、kv_cache_kernel_block_id）全部改掉：

```cpp
// Unified accelerator predicate (must match the pack/unpack classification
// below, which treats PrivateUse1/NPU tensors as device-resident too).
auto is_accel = [](const torch::Tensor& t) { return t.is_cuda() || t.is_privateuseone(); };
if (inputs.combo_tokens.defined() && is_accel(inputs.combo_tokens)) {
    device_bits |= GptModelInputDeviceBit::kDeviceBitComboTokens;
}
// ...其余五个字段同理
```

**现状说明**：Ascend TP>1 目前还没实现（只能单卡），所以这个 bug 还没实际炸过——这是提前把坑填了。评审要的 TP=2 测试因此做不了，回复评审时已说明推迟到 TP 支持落地时补。

### 5. `rtp_llm/cpp/models/PyWrappedModel.cc` —— 9 处"只认 CUDA"的判断全部认上 NPU

**评审说什么**：这个文件把 C++ 模型输入转成 Python 模型要的格式。里面一堆地方用 `is_cuda()` 判断"张量在不在设备上"，NPU 张量（`is_privateuseone()`）全部被误判为"在 CPU 上"，后果包括：
- 走 CPU 分支去调 `pin_memory()`——对 NPU 张量直接报错；
- 把 NPU 显存地址当主机内存指针交给异步写线程——读写出错；
- 该走设备直通路径的走了 host 中转——多余拷贝甚至错误。

**改了什么**（9 处，全部是同一类修法 `is_cuda()` → `is_cuda() || is_privateuseone()`）：

| 位置 | 函数 | 修复的意义 |
|------|------|-----------|
| ~170 | `normalize_i32` | NPU 张量走设备分支，不再 pin_memory |
| ~189 | `to_device_i32` | NPU 张量直通，不再被当 host 源搬运 |
| ~206 | 非 CUDA 平台的 host 提升循环 | NPU 上的长度张量也正确降回 host |
| ~211 | 混合 host/device 归一检查 | NPU prefix_lengths 也被正确处理 |
| ~259 | context 元数据分支选择 | NPU 输入不会错误进入 host 累加分支 |
| ~317 | `plus_1_to_device` | NPU 张量设备上 +1，不再误走 host |
| ~340/345 | `calculatePaddingOffsetDeviceAware` | NPU 输入的 padding offset 分支正确 |
| ~391/421 | `host_kv_cache_offset`（两处） | NPU 块表先 `.cpu()` 再给异步 writer，不再传设备地址 |
| ~508 | `to_host` lambda | cache-store 的 host 镜像正确回迁 |
| ~1151/1229 | micro-batch 的 `input_lengths_host`（两处） | NPU 长度张量正确 `.cpu().pin_memory()` |

另在文件里加了一个共用谓词并写明注释：

```cpp
// Accelerator-resident predicate: must cover CUDA *and* PrivateUse1 (NPU)
auto is_accel = [](const torch::Tensor& t) { return t.is_cuda() || t.is_privateuseone(); };
```

**对 CUDA/ROCm 的影响**：零。原来 `is_cuda()` 为 true 的场景，`is_cuda() || is_privateuseone()` 同样为 true；只是 NPU 张量从"错误分支"挪到了"正确分支"。

### 6. `rtp_llm/cpp/normal_engine/speculative/MtpExecutor.cc` —— Ascend 上 MTP 明确说"不支持"，别让人踩坑

**背景决策**（你问过"直接修好还是 raise error 好"）：评审给的两个选项是"完整迁移"或"明确拒绝"。完整迁移 = 移植 rejection sampling 采样内核 + 十几处 `torch::kCUDA` 分配 + `is_cuda()` 约束，是个独立的大工程；而且现在 Ascend 上开 MTP 也是在第一次 decode 时报一个莫名其妙的错。**所以选 fail-fast：不支持就大声说不支持。**

**改了什么**（三件事）：

**① 平台门函数**（新增，将来迁移完只需改这一处）：

```cpp
namespace speculative {
// Ascend support is NOT fully migrated yet: rejection sampling ..., several
// torch::kCUDA allocations and is_cuda()-only device-state paths ... have no
// NPU implementation.
bool mtpExecutorPlatformUnsupported() {
#if USING_ASCEND
    return true;
#else
    return false;
#endif
}
}
```

**② 构造函数体第一句话就是门**（在任何模型/缓存资源被碰之前）：

```cpp
if (speculative::mtpExecutorPlatformUnsupported()) {
    RTP_LLM_FAIL("speculative decoding (sp_type=%s) is not yet supported on Ascend NPU: "
                 "MTP/EAGLE/DSpark executors still rely on CUDA-only rejection sampling and "
                 "device-state kernels. Disable speculative decoding (remove the spec/draft "
                 "model config) on Ascend until the migration completes.",
                 SpeculativeExecutionConfig::to_string(...).c_str());
}
```

报错信息带上了具体的 sp_type（MTP/EAGLE/DSpark）和**怎么改配置**，运维一眼知道该怎么办。

**③ 构造函数的流带上真实卡号**（配合第 3.1 项）：

```cpp
// 改前：torch::Stream(c10::Stream::DEFAULT, getTorchCudaDevice())  ← 卡号是 -1
// 改后：
collect_metrics_stream_(torch::Stream(c10::Stream::DEFAULT,
    torch::Device(torch::kPrivateUse1,
                  static_cast<c10::DeviceIndex>(params.parallelism_config.local_rank)))),
// 六个 runner 全部同样改法
```

不改这个的话，`setDevice(-1)` 会在成员初始化阶段就崩掉（而且是线程里抛异常 = 进程直接 terminate），把上面那个友好的报错信息吞掉。

**注意**：配合第 7 项 `start_backend_server.py` 的配置期检查，一共三层拒绝（启动器 → 引擎构造 → 执行器构造）。

### 7. `rtp_llm/start_backend_server.py` —— 两件事：多卡能启动 + MTP 提前拒

#### 7.1 Ascend 多卡启动路径整体不可达（P1，这条是你没粘贴、我对比 PR 评论清单时发现的）

**评审说什么**（说人话版）：启动脚本入口处有个快速通道：

```python
if not torch.cuda.is_available():
    return local_rank_start(...)   # 单进程直接跑
```

Ascend 机器上 `torch.cuda.is_available()` 永远是 False → **无论配了多少卡、world_size 是几，都只启动 1 个进程就返回了**。而配置层算好的 `local_world_size` 是按 NPU 数量来的 → 其他 rank 根本不存在 → 分布式初始化（HCCL）要么失败要么干等挂死。

**改了什么**：

```python
# Single-rank fast path only when NO accelerator backend is available:
# on Ascend torch.cuda.is_available() is false, but the NPU multi-rank
# path below must stay reachable.
if not torch.cuda.is_available() and not is_ascend():
    return local_rank_start(global_controller, py_env_configs, 0, pipe_writer)
```

`is_ascend()` 复用了仓库现成的统一设备抽象（`rtp_llm/device/device_type.py`，内部安全地 try-import torch_npu，没有 NPU 就返回 False）。修复后 Ascend 的完整链路：不再提前返回 → `device_count()` 返回 NPU 数 → 卡数和 world_size 不匹配立即报错（"不会快速失败"也修了）→ 匹配则进 `multi_rank_start` 给每张卡拉一个进程（每个进程设置自己的 `ASCEND_RT_VISIBLE_DEVICES`，这部分是之前提交里已经就位的）。

**对 CPU/GPU 机器的影响**：零（`is_ascend()` 返回 False，条件等价于原来）。

#### 7.2 Ascend + 投机解码的配置期拒绝（配合第 6 项）

在 `local_rank_start` 里、创建任何引擎资源之前：

```python
if is_ascend() and py_env_configs.sp_config.type != SpeculativeType.NONE:
    raise RuntimeError(
        f"Speculative decoding (sp_type={...}) is not yet supported on Ascend NPU: ..."
    )
```

这是三层拒绝里**最早**的一层——配置还没生效、模型还没加载就报错，信息最清楚。

### 8. `rtp_llm/models_py/bindings/OpDefs.h` —— MHA 缓存视图的 K/V 布局契约（含 ratio 逻辑解释）

**先解释 ratio 是什么**：KV cache 有两种"块" granularity——
- **物理块**（allocator 管理的单位，大小 = `seq_size_per_block`）；
- **kernel 块**（attention 算子实际读取的单位，大小 = `kernel_seq_size_per_block`，Ascend FIA 算子固定 128）。

**ratio = 物理块大小 ÷ kernel 块大小**，即"一个物理块能切成几个 kernel 块"。

**评审说什么**：物理块按"整段 K 后接整段 V"存储时，直接 `view({物理块数×ratio, 2, ...})` 是对同一块内存**线性重切**——kernel 块 0 的"V"区域实际落在了 K 数据的中间段。**ratio>1 时 attention 读到的 K/V 全是错位的**。现有测试只查形状和首地址，查不出来。

**为什么不能按评审字面方案改**（"先恢复 K/V 维度再重排"）：零拷贝要求下数学不可行——kernel 块的地址 = 物理块分量 + 子块分量（两个 stride），`view`/`as_strided` 每个维度只能有一个 stride。仅有的两条路（permute+contiguous = 每层每步全量拷贝；改池子布局 = 波及存储/恢复/PD 传输）都不可接受。

**实际采用的方案**：让**写侧定义布局**，与读侧视图对齐（这正是评审在姊妹评论里自己建议的"统一使用 kernel block table 计算 cache-write slot"，见第 9 项）：

| | 写入槽位来源 | 形成的内存布局 | 与视图的关系 |
|---|---|---|---|
| 修复前 | 物理块表 × 物理页大小 | 每物理块整 K 后整 V | ratio>1 错位 |
| 修复后 | kernel 块表 × kernel 页大小 | **每 kernel 块内 K 切片后接 V 切片** | 任意 ratio 一致 |

- cache 存储/恢复、内存连接器都是**按物理块整字节拷贝**的，对块内排布无感知，不受影响；
- **ratio=1 时两种布局字节相同**——现网 128/128 配置零行为变化。

**本文件的改动**：视图代码本身不需要变（写侧对齐后它就是对的），把这套契约写成显式文档，写进 `LayerKVCache` 的头注释和 Ascend 分支注释——防止后人按"物理整 K 整 V"的假设把它"修"回去。

### 9. `ascend_impl/ascend_attn_params.py` —— slot mapping 换 kernel 块表 + page size 可传播

**评审说什么**：这个文件负责算 KV 写入的槽位（slot_mapping）。修复前：用**物理块表**（`kv_cache_block_id`）算槽位，而 FIA 读取用的是 **kernel 粒度表**——两张表粒度不同，写入位置和读取位置对不上。想拿 `kv_cache` 对象取页大小也不行：那个字段**从来没被赋过值**，类型上也没有那个属性——所以页大小永远写死 128。块一旦被细分或配置非 128，全乱。

**改了什么**：

```python
def compute_ascend_attn_params(attn_inputs, page_size=None):   # ← 新增可选参数
    # 槽位必须按 kernel 粒度算，和 C++ 视图、FIA 块表同源
    block_table = _squeeze_block_table(attn_inputs.kv_cache_kernel_block_id)  # ← 换表
    if block_table is None:
        block_table = _squeeze_block_table(attn_inputs.kv_cache_block_id)     # 物理表仅作兜底
    if block_table is not None and block_table.device.type != "cpu":
        block_table = block_table.cpu()   # 防御：kernel 表可能来自设备
    if not page_size:
        page_size = 128                   # 缺省保持历史行为
```

配合第 10/11 项（decode/prefill 传入 `attn_configs.kernel_tokens_per_block`），**写入 scatter、槽位计算、FIA 读取、C++ 视图**四者的粒度来源全部统一。

**验证**：用张量做过三条路径的冒烟——kernel 表槽位公式正确、物理表兜底与旧公式逐位一致（不传新参数时行为不变）、缺省 128 正常。

### 10. `ascend_impl/ascend_decode.py` —— MRoPE 拒绝 + page size 传播

**评审说什么**：`support()` 没排除 MRoPE（多轴位置编码，Qwen-VL 类模型用）。Ascend 实现只生成一维位置索引、从不读 `combo_position_ids`，工厂会选中这个实现然后**静默产出错误的位置编码**。RoPE 还写死 `is_neox_style=False`。

**改了什么**（四点）：

① `support()` 加拒绝（和 CUDA 实现的同款写法）：

```python
@staticmethod
def support(attn_configs, attn_inputs):
    # MRoPE is rejected: position construction below emits 1-D indices and
    # never reads combo_position_ids, so multi-axis models would silently
    # get wrong position ids (mirrors the CUDA impl's Mrope guard).
    return not attn_inputs.is_prefill and \
           not attn_configs.use_mla and \
           attn_configs.rope_config.style != RopeStyle.Mrope and \   # ← 新增
           torch.npu.is_available()
```

拒绝后工厂遍历不到任何实现，在**模型构建期**抛 "can not find mha type"——大声失败而不是静默算错。

② 页大小从真实配置传播，替换死代码：

```python
# 改前：attn_inputs.kv_cache.seq_size_per_block if attn_inputs.kv_cache else 128  ← 恒 128
self.kernel_page_size = attn_configs.kernel_tokens_per_block or 128
```

`kernel_tokens_per_block` 是仓库既有通道（CUDA 的 flashinfer 实现就用它），C++ 侧缺省自动取 `tokens_per_block`。

③ 写侧同粒度：`AscendKVCacheWriteOp(token_per_block=self.kernel_page_size)`。

④ slot 计算传入页大小：`compute_ascend_attn_params(..., page_size=self.kernel_page_size)`。

⑤ `AscendDecodeAttnOp.page_size`（FIA 读侧）同样改。

### 12. `ascend_impl/ascend_rope_emb.py` —— is_neox_style 从配置传播

**评审说什么**：RoPE 写死 `is_neox_style=False`（半分式旋转）。交错式（GPT-J 类）模型会算错位置编码。

**改什么之前先解决一个坑**：`apply_rope_pos_ids_nhd`（纯 torch 的旋转实现）的 `is_neox_style` 参数命名是**反的**——`True` 做的是**相邻配对**（交错/GPT-J）旋转，`False` 做的是**半分**（NeoX）旋转。而 `RopeConfig.is_neox_style=True` 按仓库权威约定（`rope_emb_new.py:43` 的 `interleave = not is_neox_style`、DeepSeek/GLM 都走这条）表示半分式。所以传播要**取反**：

```python
# Repo-wide convention (see rope_emb_new.py / deepseek_v2.py):
# RopeConfig.is_neox_style=True -> NeoX half-split pairing (default),
# False -> GPT-J interleaved (adjacent-pair) pairing. The pure-torch
# helper's `is_neox_style` flag names the *interleaved* pairing when
# True -- inverted versus RopeConfig --
rope_neox = bool(self.rope_config.is_neox_style) if self.rope_config is not None else True
self.is_interleaved = not rope_neox
...
apply_rope_pos_ids_nhd(..., is_neox_style=self.is_interleaved)
```

- cos/sin 缓存保持 `interleave=False`（`[cos|sin]` 两段式）——两种配对下这个布局都正确；
- `rope_config=None` 时保持历史缺省（半分），**存量模型零行为变化**；
- 交错式模型从"算错"变"算对"。
